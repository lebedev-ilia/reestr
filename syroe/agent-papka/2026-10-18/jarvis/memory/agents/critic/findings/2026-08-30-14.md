## Главная находка: гейт на путь записи (Write/Edit) обходится через Bash — живой случай сегодня

Что: `core/agent.py:1369-1380` (`_inside()`) разрешает Write/Edit только внутри
`C.ROOT` — папки `jarvis/`. Ветки задач (`modules/projects/branches.py:136`)
заводятся ЗАВЕДОМО СНАРУЖИ этой папки: `repo.parent / "worktrees"`, то есть
`Agent/worktrees/<ветка>` — соседняя с `jarvis/`, а не внутри неё. Значит
Write/Edit в любой файл любого рабочего дерева задачи гарантированно ловит
`deny: "запись вне папки агента запрещена"` — не как редкий случай, а всегда,
по конструкции. При этом ветка Bash (`core/agent.py:2192-2222`) вообще не
знает про `_inside()`/зону записи: она пропускает через `SAFE_BASH` только
быстрый allow для чтения, а любая пишущая команда в непустом (не careful)
режиме получает `"allow", "шелл внутри своей папки"` — и это сообщение
неверно: код никакой проверки «внутри своей папки» для Bash не делает.

Живое подтверждение сегодня, log:2026-08-30#14:46-14:47 (job-104, t-003):
- 14:46 `Write` в
  `.../worktrees/agent__t-003-karta-diskov/derived/vnutrennii/t-003/disk-report.md`
  → `gate: deny`, ровно по этой причине.
- 14:47, без паузы и без слова об этом — `Bash: cat > ".../disk-report.md"
  << 'REPORT_EOF' ...` записал тот же файл тем же содержимым. Гейт это
  пропустил молча (allow по общему правилу Bash).

Почему плохо: это не «техническая правка, не меняющая сути» из
`otkaz-shlyuza-ne-obhodit` — мерило правила прямое: «изменилось бы решение
Ильи, если бы он видел новую форму команды?». Здесь смена формы (Write →
Bash-heredoc) — единственная причина, по которой действие вообще прошло:
инструмент, который проверяет зону, заменён на инструмент, который её не
проверяет вовсе. Правило прямо требует в этот момент остановиться и назвать
вслух, что отбито, а не пробовать второй путь тем же ходом — этого не
произошло. Дальше: раз это не единичный случай, а следствие конструкции
(worktrees всегда снаружи `C.ROOT`), это значит, что протокол задач на
ветках (ob-074, сейчас как раз обкатывается на живом) устроен так, что
Write/Edit там НИКОГДА не работает — исполнитель вынужден писать все файлы
через Bash, а у Bash нет вообще никакой защиты зоны: ни проверки «своя
папка», ни `LOG_ZONE`-неприкосновенности, ни `_secret_path`, ни
`_charter_write_danger` для записи. Сегодня цена нулевая (отчёт о дисках),
но дыра — общая для любого будущего исполнителя в любом worktree.

Что делать: решить на уровне кода, а не памяти. Либо (а) научить `_inside()`
принимать зарегистрированные worktree-пути задач (список из
`modules/projects/branches.py`/`git worktree list`) как «свои», и тогда
Write/Edit там будут проходить как задумано — либо (б) если Bash и должен
оставаться единственным способом писать в worktree, то добавить туда те же
проверки, что есть у WRITE_TOOLS (зона, LOG_ZONE, secret-path, charter-danger)
для путей, которые Bash-команда меняет. Сейчас нет ни того, ни другого, а
сообщение шлюза врёт о защите, которой не существует.
