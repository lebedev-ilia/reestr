## Задача
Закрыть течь изоляции по проекту в шлюзе разрешений — это пункт 4 приёмки этапа 0, пока он течёт, весь этап не закрывается. Два пункта.

1) core/agent.py: шлюз судит Bash-команду по тексту — регуляркой ищет слитное «memory/projects», а резолв реального пути по диску применяется только к словам, похожим на путь. Поэтому любое расщепление пути обходит защиту: `cd memory && find projects -name dossier.md -exec cat {} \;`, `find . -maxdepth 1 -iname '*env*' -exec cat {} \;`, сборка пути переменной шелла, `find . -name dossier.md | xargs cat`. Заменить текстовую проверку на проверку по реально резолвнутым путям на диске. Как именно — решай сам, латание по одному варианту не подходит: следующий взломщик найдёт пятый.

2) core/jobs.py (район строк 520-530): submit() принимает поле project как есть, сверки нет — роль проекта А может поставить задание с project=Б и законно уйти в чужой проект. Сверять переданный project с JARVIS_PROJECT вызывающего, расхождение — отказ, а не наследование.

Это правка ядра. Иди строго по процедуре: прогнать `./jarvis --selftest` ДО правки и знать, что было зелёным; сначала добавить падающую проверку в core/selftest.py и увидеть красное, потом чинить; в том же ходе дописать строку в memory/core_changes.md (что, зачем, файлы, проверка, как откатить, чем рискуем) — без неё гит-хук правку не пропустит; отдельный коммит по-русски о смысле, а не о файлах.

## Формат результата
Текстом, по-русски: что изменено в каждом из двух файлов и почему выбран такой способ; какие проверки добавлены в самотест; код возврата `./jarvis --selftest`; хеш коммита; отдельным абзацем — что осталось непокрытым и где, по-твоему, ещё может течь. Если не получилось — прямо сказать, что мешает, а не сдавать полработы за готовое.

## Критерии приёмки
1. Все четыре способа расщепления пути выше при заданной JARVIS_PROJECT получают отказ шлюза — проверено запуском, а не рассуждением.
2. Корневой .env не читается ни прямым именем, ни через find по маске.
3. Законная работа цела: grep по своему проекту, git status/log/show, Read своего досье, пульт modules.projects.cli, и любая работа при незаданной JARVIS_PROJECT.
4. submit() с чужим project отказывает, со своим и с пустым — работает как раньше.
5. `./jarvis --selftest` целиком зелёный, код возврата 0.
6. В memory/core_changes.md есть строка про эту правку, и коммит существует.
