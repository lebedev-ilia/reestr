**Правило:** Любая работа в поле (WebSearch, WebFetch: сбор контактов, обход сайтов, исследования) отдаётся подагенту ТОЛЬКО через mcp__memory__delegate. Инструментом Agent такие задачи не запускать: он поднимает подагента внутри моего процесса, роль worker тому не выставляется, и шлюз считает его мной — после шести запросов в поле он получает отказ и требование делегировать. В итоге подагент вместо сбора становится диспетчером и ставит собственные задания, а карточек не приносит. Agent остаётся годен для работы без поля: чтение своих файлов, разбор данных на диске, правка кода, счёт.
**Почему:** 25.08 четыре партии сборщиков (AE, AF, AG, AH) были запущены инструментом Agent. Ни одна не собрала ни одной карточки: AE уткнулась в шлюз после двух WebFetch и разложилась на три задания сырья (job-011..013), AG отдала всю партию в job-014, остальные пошли тем же путём. Сгорело около 140 тысяч токенов на четырёх диспетчеров, которые только переписали мой же бриф. Причина — в core/agent.py: is_worker() читает переменную окружения JARVIS_ROLE, а подагент из Agent живёт в моём процессе и этой переменной не имеет; счётчик поля у него свой и обнуляется только запуском отдельного процесса. Это описано в самом коде (bl-045), но правила поведения из этого сделано не было — и грабля сработала.
**Как применять:** Ставя партию сборщиков, вызывать mcp__memory__delegate по одному вызову на партию, модель sonnet, бриф самодостаточный (подагент видит только его). Признак того, что грабля повторилась: подагент возвращает отчёт словами «отдал работу через delegate», «упёрся в лимит обращений к вебу», «результат придёт отдельным уведомлением» — файла партии при этом нет. Увидел такой отчёт — не будить его SendMessage (шлюз этот вызов и не пропустит), а ставить партию заново через delegate.
