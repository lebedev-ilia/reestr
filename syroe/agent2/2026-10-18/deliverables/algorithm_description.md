# Описание алгоритмов: полигональные маски и дедупликация ТС

**Документ подготовлен по ТЗ ООО «Автоматика»**, пункты 5.2 (разработка алгоритма построения
полигональной маски, реализация дедупликации) и 103 (передача описания алгоритма построения
полигональных масок, полигональных масок и дедупликации).

Дата: 2026-10-13. Данные: разметка CVAT `task_waste_up` (7101 кадр, 8 потоков).

---

## 1. Термины (по ТЗ)

| Термин | Определение |
|---|---|
| **Полигональная маска** | заранее определённая область кадра, в пределах которой выполняется детекция/оценка |
| **Дедупликация** | механизм предотвращения повторной фиксации одного и того же транспортного средства |
| **Базовая модель** | текущая модель Заказчика, с которой сравнивается результат Работ |
| **ТС** | транспортное средство |

Отличие от распространённого понимания: здесь полигональная маска — это **зона интереса (ROI)**,
а не маска объекта. Маска объекта (instance segmentation) — другая задача, она в этом документе
не описывается.

## 2. Алгоритм построения полигональной маски

### 2.1. Постановка задачи

Для каждой камеры нужно автоматически определить область кадра, в пределах которой имеет смысл
выполнять детекцию, и представить её полигоном в нормализованных координатах. Требования:

- **воспроизводимость** — результат не должен зависеть от ручного рисования;
- **устойчивость к выбросам разметки** — единичные ошибочные боксы не должны расширять зону;
- **пригодность к согласованию** — результат должен быть предъявляем Заказчику для уточнения
  (п. 5.2 ТЗ прямо требует «согласование/уточнение полигональной маски»);
- **компактность** — полигон с разумным числом точек, а не контур из тысяч пикселей.

### 2.2. Входные данные

Разметка CVAT: для каждого кадра — набор фигур (полигоны и боксы) с классами. Кадры
сгруппированы в потоки (камера = папка + префикс имени файла), всего 8 потоков.

### 2.3. Шаги алгоритма

| Шаг | Действие | Зачем |
|---|---|---|
| 1 | Разметка группируется по потокам (камерам) | у каждой камеры своя зона |
| 2 | Все фигуры потока растрируются в общий аккумулятор: для каждого пикселя считается, сколько кадров его покрывают | объекты «голосуют» за рабочую область |
| 3 | Аккумулятор делится на число кадров → **карта активности** | устраняется зависимость от длительности серии |
| 4 | Порог по устойчивости: пиксель входит в зону, если объекты покрывали его не реже заданной доли кадров | отсекаются случайные единичные объекты |
| 5 | Морфологическая чистка: закрытие (заполнить разрывы), заполнение внутренних дыр, удаление мелких островов | зона должна быть связной |
| 6 | Извлечение контура (marching squares) | переход от растра к геометрии |
| 7 | Упрощение контура **алгоритмом Дугласа-Пекера** | полигон из десятков точек вместо тысяч |
| 8 | Нормализация координат в диапазон 0..1 (относительно размеров кадра) + фильтр по минимальной площади | независимость от разрешения |

### 2.4. Параметры и их обоснование

| Параметр | Значение | Обоснование |
|---|---|---|
| Порог устойчивости | **2 % кадров** | ниже — зона «расползается» на случайные выбросы разметки; выше — теряются редкие, но законные участки. Значение проверено анализом чувствительности (см. ниже) |
| Рабочая сетка | 512 px по длинной стороне | точность контура достаточна (≈0,2 % кадра), расчёт быстрый |
| Допуск упрощения | 0,008 от длинной стороны | даёт 11–31 точку на полигон — удобно для согласования и хранения |
| Минимальная площадь | 1 % от площади зоны | отсекает мелкие острова-артефакты |

### 2.6. Ограничения алгоритма

1. **Зона строится по разметке.** Если в какой-то области объекты не размечали, она в зону не
   попадёт. Алгоритм описывает там, где объекты *наблюдались*, а не где они *могут появиться*.
2. **Нужно достаточное число кадров.** На серии из нескольких кадров карта активности
   недостоверна; практически — от сотни кадров на камеру.
3. **Порог — предмет согласования.** Алгоритм даёт воспроизводимую зону и показывает, как она
   зависит от порога; выбор конкретного значения — решение Заказчика (п. 5.2 ТЗ).
4. **Один полигон на камеру.** Если рабочая область распадается на несколько несвязных зон,
   алгоритм вернёт несколько полигонов — это поддерживается, но на текущих данных не потребовалось.

## 3. Дедупликация транспортных средств

### 3.1. Постановка задачи

Не допустить, чтобы одно и то же ТС попало в отчёт несколько раз. По ТЗ (п. 5.2) реализация
возможна «на основе доступного трекинга, признаков или пространственно-временных критериев».

### 3.2. Что уже есть у Заказчика

В текущем конвейере (`process/waste_up_process_t.py`) применяется подсчёт по классам:

```
SAME_COUNT_NUM = 5
если один и тот же КЛАСС встретился в 5 кадрах подряд → одна фиксация, счётчик сбрасывается
```

**Ограничения этого подхода:**

| № | Ограничение | Что происходит на практике |
|---|---|---|
| 1 | Счёт по классу, а не по объекту | Две разные машины одного класса в соседних кадрах дают одну фиксацию |
| 2 | Нет пространственного критерия | Машина в любой точке кадра увеличивает тот же счётчик |
| 3 | Нет идентификации ТС | Задержавшееся ТС фиксируется повторно каждые 5 кадров после сброса |
| 4 | Дребезг детекции сбрасывает счётчик | Пропуск класса на одном кадре обнуляет отсчёт — фиксация теряется |
| 5 | Нет полигональной маски | Учитывается всё, что попало в кадр, включая нерабочие зоны |

### 3.3. Предлагаемый алгоритм

Работает в два уровня.

**Уровень 1 — трекинг (идентификация объекта).**
Каждому обнаруженному объекту присваивается идентификатор трека. Используется **ByteTrack** —
штатный трекер библиотеки Ultralytics, подключаемый как
`model.track(frame, persist=True, tracker="bytetrack.yaml")`. Документация библиотеки отдельно
предупреждает: `persist=True` допустим **только для последовательных кадров одного потока**,
иначе состояние трекера переносится между несвязанными кадрами. В боевом режиме кадры приходят
из одного видеопотока, поэтому условие выполняется.

**Уровень 2 — пространственно-временная склейка (восстановление потерянных треков).**
Если трек потерялся (перекрытие, кратковременный пропуск детекции) и через несколько кадров
рядом появился новый идентификатор, он считается тем же ТС. Критерии:

- тот же класс объекта;
- последняя позиция потерянного ТС не дальше `reid_dist` от нового;
- прошло не более `reid_frames` кадров;
- это ТС не видно в текущем кадре другим треком (иначе склеятся два разных объекта).

**Регистрация фиксации.** ТС регистрируется **один раз** — при первом появлении внутри
полигональной маски. Дальнейшие кадры с тем же идентификатором новую фиксацию не создают.

**Учёт полигональной маски.** Проверяется центр объекта (тест «точка внутри полигона»);
объекты вне зоны в фиксации не попадают, но остаются в статистике детекций.

**Классы.** Дедуплицируются только ТС (`car`, `van`, `truck`, `garbagetruck`, `waste_truck`).
Прочие классы (например, отходы) не дедуплицируются — по определению ТЗ дедупликация относится
к транспортным средствам.

### 3.4. Параметры

| Параметр | Значение | Смысл |
|---|---|---|
| `reid_frames` | 25 кадров | сколько кадров держим потерянный трек для склейки |
| `reid_dist` | 0,06 кадра | максимальное расстояние между центрами (нормированное) |
| `iou` (отладочный трекер) | 0,3 | порог сопоставления по IoU |
| Список классов ТС | car, van, truck, garbagetruck, waste_truck | что считаем ТС |

|---|---|---|---|---|

доля детекций признана повторами.

Прогон с моделью и ByteTrack (8 камер, 6632 кадра) дал более высокие значения (0,964–0,998),
**однако эти цифры не являются подтверждением качества** — см. п. 3.6.

### 3.6. Ограничения и условия корректной работы

1. **Требуется непрерывный видеопоток.** Алгоритм опирается на последовательность кадров.
   Аннотированный набор `waste_up` — не видео, а разреженная выборка кадров по событию:
   проверка по отметкам времени на кадрах показала, что соседние кадры разнесены на **дни**
   (например, 23/02/2022 → 24/02/2022 → … → 25/03/2022), при этом внутри события кадры идут
   секундами. Покадровый трекинг на такой выборке некорректен: на весовой разные машины встают
   на одно и то же место, и трекер склеивает их в одну. Именно поэтому прогон «с моделью» дал
   ложные 0,998 на части камер.
2. **Для проверки нужны метки времени кадров или короткое видео.** Тогда дедупликация
   проверяется в режиме, близком к боевому.
   **Что конкретно требуется (минимум):** либо метки времени кадров (если ведутся в системе
   Заказчика), либо **один видеоклип 1–2 минуты** с любой камеры — непрерывная запись проезда
   одной-двух машин. Переделывать весь набор не нужно: для проверки алгоритма достаточно
   короткого непрерывного фрагмента.
3. **Метрика качества дедупликации требует согласования** (п. 5.3 ТЗ). Предлагаемая базовая
   метрика — коэффициент дедупликации; для полноты нужен эталон числа ТС на клипе, иначе
   невозможно отличить «склеил лишнее» от «склеил правильно».
4. **Один поток — один процесс.** Состояние трекера нельзя переносить между камерами:
   в реализации каждая камера обрабатывается отдельным процессом.

## 4. Воспроизведение

```bash
# 1. Построение полигональных масок по разметке CVAT
python3 my_agent/build_polygon_mask.py \
    --zip "<архив CVAT>" --out files/polygon_masks \
    --coverage 0.02 --grid 512 --epsilon 0.008

# 2. Дедупликация на разметке (без модели — проверка логики)
python3 my_agent/dedup_events.py --mode cvat \
    --zip "<архив CVAT>" --masks files/polygon_masks/polygon_masks.json \
    --out files/dedup

# 3. Дедупликация с моделью и ByteTrack (на сервере, по одному процессу на камеру)
python3 my_agent/dedup_events.py --mode yolo \
    --model <веса> --manifest <список кадров камеры> --camera "<камера>" \
    --masks polygon_masks.json --out <каталог>
```

Зависимости: Python 3, numpy, scipy, scikit-image, matplotlib (для оверлеев);
для режима с моделью — ultralytics.

## Сверка алгоритма построения масок с практикой (добавлено позже)

**Честное признание:** изначально алгоритм был написан **без опоры на источники** — из общих
знаний. Это нарушение внутреннего правила «сначала документация». Сверка проведена позже,
и вот её результат.

**Что делает индустрия.** Документированный конвейер выделения зоны (пример — блок детекции
движения Roboflow, [docs.roboflow.com](https://docs.roboflow.com/workflows/blocks/blocks/video-processing/motion-detection)):

1. модель фона (MOG2) → маска движения;
2. **морфологические операции** для удаления шума и объединения близких областей;
3. **поиск контуров** с фильтрацией по минимальной площади;
4. **упрощение контуров**;
5. зона задаётся полигоном.

Их параметры по умолчанию: минимальная площадь контура 200 px², ядро морфологии 3 px
(эллипс), порог 16 (в диапазоне 8–32), история 30 кадров.

**Совпадения с нашим алгоритмом:** шаги 2–4 совпадают полностью — морфологическая чистка,
поиск контуров с отсечением по площади, упрощение контура (у нас — Дуглас-Пекер). То есть
структура конвейера соответствует практике, хотя писалась независимо.

**Принципиальное отличие:** в индустрии зону обычно **рисует оператор вручную**
(`detection_zone` — входной параметр), а не генерирует алгоритм. У нас ТЗ (п. 5.2) требует
именно **разработать алгоритм построения**, поэтому автоматическая генерация — вынужденное
и правильное для этой задачи решение.

**Второе отличие:** источник данных. В практике зону строят по **движению** (вычитание фона),
у нас — по **размеченным объектам** (карта покрытия). Причина объективная: у нас нет видео,
есть только кадры событий, зато есть разметка. Подход обоснован, но это наша адаптация,
а не стандарт.

**Что было добавлено по итогам сверки:** измеримый критерий качества зоны. Практика требует
проверять зону, а не смотреть на неё глазами. Проверено: **96,9 % размеченных объектов
попадают внутрь зоны своей камеры** (1504 из 1552). Зона не отсекает полезные детекции.

**Что осталось нашим и не подтверждено источником:** конкретные значения параметров
(`coverage = 0,02`, ядро 5×5, `epsilon = 0,008`, `min-area = 1 %`). Они подобраны по анализу
чувствительности (`threshold_sensitivity.json`), но внешнего подтверждения у них нет —
в отличие от шагов конвейера.
