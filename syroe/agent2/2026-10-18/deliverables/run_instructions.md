# Инструкция по запуску

Документ описывает, как запустить переданные модели и скрипты. Составлен по п. 7.2, 9 и 11 ТЗ.

---

## 1. Состав передаваемого программного обеспечения

| Файл | Назначение |
|---|---|
| `detect.py` (или `best.pt`) | модель детекции ТС (задача 1) |
| `build_polygon_mask.py` | построение полигональных масок (зон интереса) по разметке |
| `dedup_events.py` | дедупликация фиксаций ТС |
| `cvat2yolo_types.py` | конвертация разметки CVAT в формат YOLO с разбиением по атрибутам |
| `fill_service.py` | оценка заполненности (кузова либо зоны) |
| `stream_naming.py` | определение камеры и номера кадра по имени файла |
| `weights/best.pt` | веса модели детекции ТС |
| `weights/best_seg_types.pt` | веса модели типов отходов и состояний контейнера |
| `polygon_masks.json` | координаты зон по 8 камерам |

## 2. Требования к окружению

### Сервер (обучение и оценка)

| Компонент | Версия, на которой проверялось |
|---|---|
| Python | 3.12 |
| PyTorch | 2.7.1 + CUDA 12.8 |
| ultralytics | 8.4.175 |
| GPU | NVIDIA RTX 5080 (16 ГБ) |

Установка:

```bash
python -m venv venv && source venv/bin/activate
pip install ultralytics opencv-python-headless pillow numpy
```

> **Важно:** используется именно `opencv-python-headless`. Обычный `opencv-python` требует
> системную библиотеку `libGL`, которой на сервере нет, и импорт `cv2` падает.

### Jetson Nano 4 ГБ

| Компонент | Версия, на которой проверялось |
|---|---|
| L4T / JetPack | R32.6.1 / JetPack 4.6 |
| ОС | Ubuntu 18.04.6 LTS |
| Python | 3.6.9 |
| TensorRT | 8.0.1.6 |
| PyTorch | 1.10.2 (**сборка без CUDA**) |

> На устройстве **нет** `ultralytics`, `pycuda` и `cuda-python`, и ставить их не требуется:
> инференс идёт через `trtexec` (штатная утилита TensorRT). Прямой вызов движка из Python
> невозможен — без `pycuda`/`cuda-python` не выделить память на GPU.

## 3. Запуск на сервере (эталон, PyTorch)

### 3.1. Детекция ТС на изображении или каталоге

```bash
python -c "
from ultralytics import YOLO
m = YOLO('weights/best.pt')
r = m.predict('путь/к/кадру.jpg', imgsz=640, conf=0.25, iou=0.6)[0]
for b in r.boxes:
    print(m.names[int(b.cls)], float(b.conf), b.xyxy.tolist())
"
```

### 3.2. Оценка заполненности

Заполненность кузова (основной режим):

```bash
python fill_service.py --mode vehicle \
    --source путь/к/каталогу_с_кадрами \
    --weights weights/best.pt \
    --out результат.json
```

Доля площади рабочей зоны, занятая отходами (дополнительный режим):

```bash
python fill_service.py --mode zone \
    --source путь/к/каталогу \
    --camera auto \
    --masks polygon_masks.json \
    --weights weights/best.pt \
    --out результат.json
```

Результат — JSON:

```json
{
  "summary": {"mode": "vehicle", "frames": 1061, "mean_fill_percent": 37.34,
              "max_fill_percent": 90.65, "alarms": 44, "warnings": 165},
  "results": [{"file": "кадр.jpg", "vehicles": [
      {"vehicle_class": "truck", "fill_percent": 62.5, "level": "alarm",
       "recommendation": "Заполнено — требуется вывоз"}], "level": "alarm"}]
}
```

### 3.3. Построение полигональной маски

```bash
python build_polygon_mask.py --zip архив_разметки.zip --out каталог_масок \
    --coverage 0.02 --grid 512 --epsilon 0.008 --min-area 0.01
```

На выходе: `polygon_masks.json` (координаты зон по камерам) и оверлеи
`mask_<камера>.png` для визуального согласования.

### 3.4. Дедупликация

Проверка на размеченных данных:

```bash
python dedup_events.py --mode cvat --data каталог_датасета --out результат.json
```

Боевой режим (по видеопотоку, с трекингом):

```bash
python dedup_events.py --mode yolo --source rtsp://... --weights weights/best.pt
```

## 4. Запуск на Jetson Nano (TensorRT)

### 4.1. Подготовка движка

Движки TensorRT **привязаны к конкретному GPU** — собранный на сервере движок на Jetson
не заработает. Порядок:

1. на сервере: экспорт модели в ONNX
   ```bash
   python -c "
   from ultralytics import YOLO
   YOLO('weights/best.pt').export(format='onnx', imgsz=640, opset=12, simplify=True)
   "
   ```
2. перенести ONNX на Jetson (например, `rsync`);
3. на Jetson: сборка движка под его GPU
   ```bash
   /usr/src/tensorrt/bin/trtexec --onnx=модель.onnx --saveEngine=модель_fp16.engine \
       --fp16 --workspace=16 --avgTiming=1 --minTiming=1
   ```

> **Сборка занимает около 7 минут и сильно нагружает устройство.** На Jetson Nano 4 ГБ
> собирать движки с батчем больше 1 не следует: при батче 8 сборка упирается в память
> (свободной оставалось 33 МБ из 1971). Рекомендуется батч 1.

### 4.2. Инференс

```bash
# подготовка входа: letterbox до 640x640, нормализация, формат NCHW FP32
# затем:
/usr/src/tensorrt/bin/trtexec \
    --loadEngine=модель_fp16.engine \
    --loadInputs=images:вход.bin \
    --exportOutput=выход.json \
    --iterations=1 --warmUp=0 --duration=0
```

Выход — JSON со списком тензоров; у модели детекции ТС тензор `output0` имеет форму
`(1, 9, 8400)`: 4 координаты рамки и 5 оценок классов по 8400 позициям.

Постобработка (отбор по порогу и NMS) выполняется отдельно.

> **Важно про NMS.** Если применяете `cv2.dnn.NMSBoxes`, помните: эта функция **не знает
> о классах** и подавляет рамки разных классов друг другом. Ultralytics делает NMS по каждому
> классу отдельно. Неверный NMS дал нам ложную «потерю» 10 пунктов mAP на FP16 — на этой
> ошибке потеряно время, поэтому предупреждение оставлено в инструкции.

### 4.3. Контроль нагрузки на устройство

Устройство слабое и на нём работает боевой сервис. Пороги защиты, прописанные в самом
устройстве: `passive 97 °C`, `hot 100 °C`, `critical 102 °C`. Рабочий порог остановки
рекомендуется держать на **80 °C**. За время наших работ температура не превышала 48,5 °C.

## 6. Известные ограничения

1. **Jetson перезагружается каждые 30 минут** — аппаратная проблема (вероятно, питание).
   Любая задача длиннее ~29 минут прерывается. Требует решения на стороне Заказчика.
2. **11 файлов датасета недоступны** (`Permission denied`) — при воспроизведении их нужно
   пропускать, а не считать ошибкой.
3. **Класс `waste`** в детекции ТС имеет невысокую точность (mAP@0,5:0,95 = 0,725):
   объекты аморфные. Проверенные способы повышения качества (длинное обучение, аугментации
   редкого класса, повышенное разрешение, более тяжёлая модель) прироста не дали —
   ограничение в данных, а не в модели.
4. **Базовая модель Заказчика не покрывает контейнерные площадки** — на данных задачи 2
   она не находит объектов вовсе.
