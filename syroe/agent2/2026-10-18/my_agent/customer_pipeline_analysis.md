## 2. Как устроен их конвейер

```
медиа (фото/видео) → [Redis-очередь] → waste_up_process_t.py → process_file.py
                                          (dedup)                (YOLOv5 detect.run)
```

**`yolov5/process_file.py`** (2,8 КБ) — инференс:
- принимает изображение или видео, гоняет `detect.run` с весами и `data/waste_up.yaml`;
- сохраняет боксы в JSON: `label`, `confidence`, `box`, `area`, `box_x_center`, `box_y_center`;
- **полигональная маска НЕ применяется** — детекция идёт по всему кадру.

**`process/waste_up_process_t.py`** (7,1 КБ) — сервис на Redis:
- слушает очередь `l.waste_truck_request`, скачивает медиа, зовёт `process_file`;
- возвращает результат вложением через callback;
- здесь же живёт дедупликация (см. ниже).

## 3. Их дедупликация — вот что мы должны улучшить

```python
SAME_COUNT_NUM = 5
...
for f in data['frames']:
    for b in f['boxes']:
        l_list.append(b['label'])
for k in list(found_objs.keys()):
    if k not in l_list:
        del found_objs[k]          # класс пропал из кадра — счётчик обнулён
for l in l_list:
    found_objs[l] = found_objs.get(l, 0) + 1
    if found_objs[l] >= SAME_COUNT_NUM:
        do_send_attachment = True   # 5 кадров подряд — отправляем фиксацию
        del found_objs[l]           # и обнуляем
```

**Алгоритм:** если один и тот же **класс** встречается в **5 кадрах подряд**, это одна фиксация;
после срабатывания счётчик сбрасывается.

**Слабые места (то, что улучшает наша работа):**

| № | Проблема | Следствие |
|---|---|---|
| 1 | Счёт по **классу**, а не по объекту | Две разные машины одного класса в соседних кадрах дают срабатывание, будто это одна |
| 2 | Нет пространственного критерия | Машина в любом месте кадра увеличивает тот же счётчик |
| 3 | Нет идентификации ТС | Одна и та же машина, задержавшись, фиксируется повторно каждые 5 кадров после сброса |
| 4 | Дребезг детекции сбрасывает счётчик | Если класс пропал на 1 кадр, отсчёт начинается заново — фиксация теряется |
| 5 | Нет полигональной маски | Считается всё, что попало в кадр, включая зоны вне рабочей области |

## 4. Что это значит для ТЗ

1. **Задача «разработка алгоритма построения полигональной маски» (п. 5.2) — не дублирование:**
   в текущем конвейере маски нет вообще. Наш алгоритм закрывает реальный пробел.
2. **Наша дедупликация (трекинг + ROI + пространственно-временная склейка) адресует все 5 слабых
   мест** — это и есть содержательное улучшение, которое требуется по п. 5.1.
3. **Сравнение с базовой моделью надо ограничить 4 общими классами** либо дообучать под 8 классов.
4. **Заказчик уже смешал обе задачи в одной модели** (ТС + морфология отходов) — это ориентир
   для задачи 2.

## 5. ⚠️ Эксплуатационное предупреждение

На Jetson **работает боевой сервис**: процессы `waste_up_process_t.py` (3 шт.), Redis активен,
очередь пуста. Плюс предупреждение Заказчика: «модель старая, работает ещё с SD-карты, так что
скорость и ресурс там ниочень — сильно дрочить его не стоит».

**Правила работы с этим устройством:**
- ничего не останавливать и не перезапускать в `~/work/waste_up` и `~/app_waste_monitor`;
- свои файлы держать отдельно (например, `~/agent2/`), не писать в их каталоги;
- не запускатьдлительное обучение и тяжёлые бенчмарки; замеры — короткими прогонами;
- минимизировать запись на SD-карту (она изнашивается), логи — маленькие;
- перед любыми изменениями — согласование с Заказчиком.
