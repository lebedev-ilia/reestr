## Замечание 1 (новое, подтверждено живьём в этом же заходе) — `sed -n` без `-i` целиком блокируется зональным шлюзом для ролей

**что** — `core/agent.py:301-308`, `SAFE_BASH`. Список разрешённых для чтения
команд (`ls|pwd|cat|head|tail|wc|tree|find|grep|rg|which|file|stat|du|df|echo|
date|env|printenv|...|ps|pgrep|pstree|pidof|uptime`) не включает `sed`. В
`_role_zone_bash_danger` (~строка 2100-2109) любая команда, не подошедшая под
`SAFE_BASH`/`ZONE_PY_C_HEAD`/`ZONE_PY_CLI_HEAD`, получает жёсткий отказ «У тебя
есть своя зона записи...» — без разбора, есть ли в ней вообще запись. Поймал
на себе дважды подряд в этом заходе: `sed -n '500,540p' core/jobs.py` и
`sed -n '1,5p' core/agent.py` (оба чтения, без `-i`, без записи куда бы то ни
было) получили полный отказ; при этом `cat` того же файла через Read/Bash
проходит без вопросов.

**почему плохо** — `sed -n` для чтения диапазона строк — такой же стандартный
приём, как `head`/`tail`, и он уже явно учтён в комментарии самого файла
(строка 348: «Чтение (cat, grep, sed -n, tail) не трогается: лог для того и
пишется» — то есть автор кода знает и подразумевает, что `sed -n` безопасен,
но забыл включить его в `SAFE_BASH`). Роль без питона под рукой (у критика
`python3 -c` разрешён только с чтением через AST-проверку, но лишний виток) в
разборе конкретных строк файла остаётся без единственного адресного
инструмента — вынужден либо читать файл целиком через Read (дороже), либо не
проверять вовсе. Это тот же класс, что уже фиксировался в LESSONS
(«моя песочница блокирует и чтение, не только запись») для `ps aux` и
`python3 -c` — те два случая с тех пор явно почищены (ps/pgrep/... и
`ZONE_PY_C_HEAD` в списке есть), а `sed -n` остался незамеченным.

**что делать** — добавить `sed` (или отдельно `sed\s+-n`) в `SAFE_BASH`, при
этом убедиться, что `ZONE_BASH_WRITE` (строка ~1767) по-прежнему ловит
`sed -i`/`sed` с записью — сейчас разрыв на запись прикрыт отдельной проверкой
`_hook_danger`/`_access_danger` по `-i`, но лучше явно развести: `sed -n` без
`-i` → чтение, `sed` с `-i`/без `-n` и без явного признака чтения → как
раньше через `ZONE_BASH_WRITE`. Проверить самотестом на обоих сценариях.
