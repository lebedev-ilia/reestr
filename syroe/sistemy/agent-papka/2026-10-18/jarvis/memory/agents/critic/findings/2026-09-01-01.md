## 1. Новый баг сортировки в modules/inbox/read.py — заглушка даты обходит собственную же только что написанную защиту

Коммит f9fb417 (00:11, bl-159) чинил реальный баг: сортировка входящих по
сырому `ts` сравнивала ISO-строки с разными смещениями как текст и врала про
порядок (задокументировано новым правилом
`memory/rules/vremya-sravnivaetsya-posle-privedeniya.md`). Фикс — сортировать
по `when_str(r["ts"])`, строке местного времени.

Но `when_str()` (modules/inbox/read.py:114-129) для пустого/нераспознанного
`ts` возвращает заглушку `"????-??-?? ??:??"` той же ширины — а сортировка
(строка 363: `sorted(buckets[kind], key=lambda r: when_str(r["ts"]), reverse=True)`)
по-прежнему строковая. Символ `?` (ASCII 63) больше любой цифры (ASCII
48-57), поэтому при `reverse=True` (свежие сверху) строка `"????-??-??
??:??"` окажется ВЫШЕ любой настоящей даты, включая самые свежие письма.

Почему плохо: `ts` пустеет, когда у письма не распарсился заголовок Date
(строки 331-334, `except Exception: when = ""`) — это реалистично для раздела
«мимо рассылки» (личная почта, автоматика, разные отправители). Итог — письмо
без даты будет показано ПЕРВЫМ, как будто оно самое свежее, ровно тот же
класс тихой лжи о порядке, который эта же правка была призвана исправить.

Что делать: сортировать не по строке заглушки, а по исходному `datetime`
(или по `ts`, приведённому к сравнимому виду с явным fallback вроде
`datetime.min`), либо после сортировки переносить пустые/кривые записи в
конец независимо от текстового представления.

Не проверено живым прогоном (моя зона не позволяет запускать код за
пределами protocol проектов) — вывод сделан по чтению кода и таблице ASCII,
логика однозначная: `'?' > '9'` в Python верно всегда.
