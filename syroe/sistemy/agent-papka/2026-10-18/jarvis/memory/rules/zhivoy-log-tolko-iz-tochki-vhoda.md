**Правило:** Право писать в memory/log есть только у процесса, который поднял его вызовом memory.mark_live() в своей точке входа (run.py, демон ВК, воркер подагента, notify). Любой разовый скрипт — проверка руками, отладка, эксперимент из Bash — пишет в derived/manual/log с предупреждением, и это нормальный исход, а не поломка. Право не наследуется через окружение: иначе его получил бы каждый дочерний процесс. Мусор, уже осевший в живом логе, не удаляется, а отсекается при ЧТЕНИИ — сигнатурой в core/fixtures.py, закрытой окном по времени; фильтровать по одному имени инструмента нельзя.
**Почему:** 25.08 ручные проверки шлюза по bl-047/bl-048 налили в неизменяемую зону 344 записи gate: 210 по выдуманному инструменту SomeNewTool и ещё 134 с настоящими именами Write и Bash (файл /tmp/x, команда sudo rm -rf /, удаление выдуманного дня лога). Самоаудит показывал 219 отказов шлюза за сутки, из которых живых было 79 — то есть картина «что меня останавливало» была искажена втрое, навсегда. Самотесты к тому моменту уже были закрыты guard'ом, но ручные проверки о нём не знали: закрывать надо не тест, а запись.
**Как применять:** Новая точка входа — первой строкой memory.mark_live(), иначе её след потеряется в derived. Разовая проверка — mark_live НЕ звать: пусть пишет в derived. Понадобилось отсечь уже натёкшее — добавить сигнатуру в core/fixtures.py с описанием словами и с окном GATE_WINDOW_END, а не расширять фильтр по имени инструмента: широкий фильтр тихо съест живые отказы, и «шлюз ничего не отбивал» будет значить «фильтр всё вычистил». Каждую новую сигнатуру испытывать мутацией: расширить её до общего вида и убедиться, что проверка «живой отказ карантин не трогает» краснеет.
