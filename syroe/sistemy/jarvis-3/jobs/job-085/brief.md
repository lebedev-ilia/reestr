## Что делает сам

1. Заводишь каталог `jarvis/memory/projects/` с README.md (одна строка: что здесь живёт и кто владелец) и внутри — проект-полигон `vnutrennii/` по составу из раздела 6.1 документа: dossier.md, decisions.md (журнал решений, владелец Jarvis), obligations.md, backlog.md (своя очередь задач), tasks/ (задачи), artifacts/ (артефакты), knowledge/ (знания команды), correspondence.md (выжимка переписки). Файлы заводи пустыми-с-шапкой, не выдумывай содержание.
2. Пишешь модуль `jarvis/modules/projects/`: `__init__.py`, `tasks.py` (ядро протокола), `cli.py` (пульт), `README.md`.
3. Протокол задачи. Задача живёт в `memory/projects/<проект>/tasks/<id>/` и содержит ровно три файла:
   - `task.md` — пишет тимлид, исполнителю только чтение. Разделы в порядке приоритета: даты, цели, критерии, границы, связи, материалы. ПОТОЛОК 100 СТРОК — проверяется машинно, при превышении создание/правка задачи отбивается с понятной ошибкой.
   - `task.json` — критерии приёмки: список пунктов, у каждого `id`, `text`, `passes: false`, `checked_at: null`, `checked_by: null`. Плюс шапка: id задачи, проект, тимлид, исполнитель, даты (created, planned_due, started, finished), круги доработки (список), статус.
   - `progress.md` — ведёт исполнитель: журнал работы, план проверки каждого критерия, вопросы, фактические даты.
4. Функции модуля (все с проверками, а не на доверии):
   - `create(project, title, ...)` — заводит задачу, ставит дату создания и плановую дату, генерирует id вида `t-001`.
   - `plan(task, text)` — исполнитель записывает план проверки в progress.md; отбивать пустой/общий план: требовать, чтобы план упоминал каждый id критерия из task.json, иначе ошибка со списком непокрытых.
   - `submit(task)` — исполнитель сдаёт: ставит фактическую дату, статус `submitted`. Закрыть задачу сам исполнитель НЕ может — `accept` из режима исполнителя отбивается.
   - `accept(task, verdict)` — только тимлид: меняет `passes` у критериев, ставит «Выполнено» либо круг доработки с датой и пунктами (круг дописывается в task.md).
   - `check(task)` — машинные проверки доказательства выполнения по разделу 4 документа: артефакт существует, размер ненулевой, время создания позже старта задачи; все критерии `passes: true`; task.md не длиннее 100 строк; task.json не потерял пунктов относительно первой версии (сравнение с git-историей файла — подмена критериев задним числом это находка).
   - `overdue(project)` — список просроченных задач с причиной, для сводки.
   - `status(project)` — машинная сводка: сколько задач в каком статусе, кто чем занят, что стоит.
5. CLI: подкоманды `create`, `plan`, `submit`, `accept`, `check`, `status`, `overdue`, `list`. Русские сообщения об ошибках.
6. Самотест: отдельный файл `jarvis/core/projects_selftest.py` по образцу `jobs_selftest.py`, подключённый в `core/selftest.py`. Обязательно проверить: потолок 100 строк отбивается; исполнитель не может закрыть задачу; удаление или правка текста пункта в task.json ловится; план без покрытия всех критериев отбивается; артефакт нулевого размера не проходит `check`. САМОТЕСТ РАБОТАЕТ ТОЛЬКО НА ВРЕМЕННОМ КАТАЛОГЕ в derived/, в memory/ он не пишет ничего — это жёсткое правило, нарушение = провал задания.
7. Прогоняешь `jarvis/.venv/bin/python jarvis/run.py --selftest` (или как он зовётся в README) целиком и добиваешься зелёного.
8. Коммитишь свою работу отдельными коммитами, ТОЛЬКО свои файлы (перечисляй пути явно, `git add -A` запрещён): modules/projects/**, core/projects_selftest.py, core/selftest.py, memory/projects/**.
