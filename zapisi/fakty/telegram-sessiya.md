**Telegram настроен через userbot-сессию аккаунта Ильи (@haunteedFamily, id 5053329284),
а не через бота. Сессия лежит в `telegram-mcp/.env` (секрет): читать можно
любые чаты аккаунта, отправка — только с подтверждения владельца. Одновременно сессию может
держать один клиент — MCP берёт замок, иначе Telegram гасит сессию.**

## Как устроено

- **Bot API не подходит:** бот видит только сообщения, адресованные ему; личную переписку
  и историю читать не может. Поэтому нужен доступ к аккаунту через MTProto (api_id + api_hash +
  session string) — это и есть userbot.
- Сессия уже создана и проверена: `CONNECTED: True`, `AUTHORIZED: True`, аккаунт **Илья**,
  @haunteedFamily, id 5053329284. Повторная авторизация не нужна.
- Чтение в рабочей папке — `my_agent/tg_read.py` (list/read/search/whoami, время UTC+10) через
  Telethon; выгрузки складываются в `telegram/`: `00_dialogs.txt` (200 чатов),
  `chat_126461673.txt` (Сергей Редькин, 29 сообщений) и др. Скрипты **не отправляют** сообщения
  и **не помечают прочитанным**.
- Отправка — через ту же сессию, с тем же замком, что у MCP-сервера (см.
  [[telegram-cherez-sessiyu]]). Живая проверка 17.10: сводка ушла в «Избранное»,
  `message_id 330347`.

## Замок (почему нельзя два клиента)

Telegram запрещает использовать один ключ авторизации с двух IP одновременно: второй клиент
получает `AuthKeyDuplicatedError`, и **сессия может быть погашена для обоих**. Поэтому
MCP-сервер перед подключением берёт на сессию файловый замок: второй процесс ждёт 20 секунд
(`TELEGRAM_LOCK_GRACE_SECONDS`) и выходит с ошибкой, называя PID держателя, — вместо гонки
в `connect()` (описание замка — в документации `telegram-mcp`, вне реестра: каталог секретов
не копировался). Если несколько клиентов на одной машине выходят в сеть с одного IP, замок можно
сделать разделяемым: `TELEGRAM_SESSION_LOCK=shared`. Альтернатива для нескольких клиентов —
пул сессий `TELEGRAM_SESSION_STRINGS`, каждая со своим замком.

Правила: одна сессия — один клиент; замок берётся **до** подключения; ошибку «другой процесс
уже держит сессию» не обходить, а ждать или переключать клиента.

## Что можно и чего нельзя

**Можно:** читать любые диалоги аккаунта, историю, медиа; искать по чатам; отправлять
сообщения от имени аккаунта — только по подтверждению владельца и в согласованный чат.

**Нельзя:** держать второй клиент на той же сессии; публиковать session string и api_hash;
массовые рассылки (флуд-лимиты и риск бана); работать без подтверждения владельца при отправке.

**Ограничение канала:** сеть периодически режет доступ к Telegram (первый коннект — таймаут,
второй — успех); для устойчивости нужен VPN/прокси. WireGuard на момент работ был опущен,
`sudo` из агентской среды недоступен.
