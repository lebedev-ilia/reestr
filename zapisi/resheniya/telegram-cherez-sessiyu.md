**Решено 17.10: бот-токен не заводим — отправляем через уже настроенную userbot-сессию
аккаунта, с тем же замком, что у MCP-сервера. Если сессию держит MCP, отправка честно
отказывается и не сжигает её. Живая проверка: сводка ушла в «Избранное», message_id 330347,
аккаунт @haunteedFamily.**

## Решение

| Вопрос | Решение |
|---|---|
| Канал доставки сводки | **Telegram** (решение владельца) |
| Бот или сессия | **сессия**, без бот-токенов: «тг же уже настроен, ненадо никаких бот-токенов» |
| Замок | тот же `SessionLock`, что у `telegram-mcp`, режим **shared** |
| Если сессия занята | отправка **отказывается** с понятной ошибкой, второй клиент не подключается |
| Проверка | живая отправка в «Избранное», `message_id 330347` |

## Причина

- Bot API не читает личные переписки — для чтения всё равно нужна userbot-сессия.
- Второй клиент на той же строке сессии Telegram считает дублем ключа и может погасить
  сессию для обоих (`AuthKeyDuplicatedError`), а это основной канал связи владельца.
- Замок решает это до подключения: MCP или отправка берут его первыми, второй участник ждёт
  и выходит, а не ломает сессию.
- Бот-токен — это ещё один секрет и ещё один канал; при готовой сессии он не нужен.

## Что было по пути (важно)

Первая живая отправка не сработала: значения `TELEGRAM_*` не передавались процессу — исправлено.
Сам факт «код отправляет» ничего не доказывал: проверка была по `message_id`, то есть по факту,
а не по намерению кода.

## Следствия

- **Отправка — только с подтверждения владельца**: система готовит текст, отправляет по команде.
- Один клиент на сессию; при параллельной работе — `shared`-замок или пул сессий.
- Документ `docs/ekspluataciya.md` (20:00) описывает бот-токен — это **устаревшая** часть:
  решение 22:00 её отменяет. Документ не переписан; при чтении верить записи, а не разделу.
- Устройство сессии и её ограничения — см. [[telegram-sessiya]].
